# 仓库管理系统开发计划

更新：2026-10-22。本文件是**开发路线和验收说明**，不是已完成功能清单。每项任务开始前，先核对当时的代码、数据库和 `docs/progress.md`；文件名和实现方式可以在 Review 时调整。

## 怎么使用这份计划

1. **一次只领取一个任务。**先弄清业务规则，再由开发者亲自编写核心业务代码。
2. 每个任务按“业务目的 → 开发重点 → 验证场景 → 完成条件”阅读。暂时只看当前任务的任务卡；后面的卡片用于了解方向。
3. 导师提供拆解、伪代码和 Code Review。开发者完成代码后再联调、测试和修正。
4. 只有 Review、相关验证和记录都齐全，才在 `docs/progress.md` 标为完成。仅创建类或编译通过不算完成功能。
5. 完成可验证的小段工作后提交 Git；推送前检查暂存内容，确保没有数据库密码、密钥或本地数据。

下文提到的 Java 文件默认位于 `src/main/java/org/whiteicetea/warehousemanagementsystem/`；测试文件位于对应的 `src/test/java/` 包。数据库设计以 `docs/database-design.md` 为准，接口目标以 `docs/api-design.md` 为准。**这些设计文档描述的是目标，不自动代表当前服务已经做到。**

## 当前任务：T02 统一响应与异常

### 业务目的

客户端不能只看一句错误文字来判断结果。接口需要同时给出正确的 HTTP 状态码和稳定的 `code`、`message`、`data` 正文。例如商品不存在时返回 HTTP 404 和 `GOODS_NOT_FOUND`，而不是把所有错误都当成功返回。

### 开发重点

- `ApiResponse<T>` 表示统一正文；`ErrorCode` 维护稳定错误码及其 HTTP 状态；`BusinessException` 把业务失败交给全局处理器。
- `GlobalExceptionHandler` 分别处理业务异常、非法请求、错误 JSON、不支持的 HTTP 方法或媒体类型，以及未预料的服务错误。意外错误要记录到服务日志，响应中不暴露 SQL、堆栈或密码。
- T02 负责公共机制；商品列表和详情的成功响应迁移在 T03，新增与修改响应迁移在 T04、T05。

### 验证和完成条件

- 已有证据：统一业务 404、统一 405 的手工响应；400 的开发者反馈。
- 还需核对：畸形 JSON 的实际 400 响应、415、500，以及有断言的针对性测试。检查 HTTP 状态码与正文同时正确。
- Review 当前实现，解决发现的问题，再把结果写入 `docs/progress.md`。**T02 目前不能标为完成。**

## P0：确认已有功能

### T01：现有商品修改接口回归（已按旧接口范围手工验收）

- **业务目的：**确认已有 `PUT /api/goods` 确实修改指定商品，避免重新开发已存在的基础链路。
- **开发重点：**本任务以联调为主，使用实际存在的商品；先 GET 保存原值，再 PUT 名称和价格，再 GET 对照。
- **验证场景：**名称、价格改变；`goodsCode`、`stockQuantity`、`createdAt` 保持不变。请求、状态码和响应保存在 `docs/progress.md`。
- **完成边界：**现有接口的手工行为已验收；DTO、受保护字段和自动化测试仍在 T04、T05 等任务处理。

## P1：商品接口边界（T02～T07）

阶段目标：商品基础能力能处理合法输入、非法输入、找不到资源和重复编码；客户端不能通过商品资料接口随意改库存。T02 当前进行中；后续任务按顺序领取。

### T03：商品列表、详情与明确的 404

- **业务目的：**同一个商品读取接口应有稳定的输出格式；不存在的商品应得到可识别的 404。
- **开发重点：**建立 `GoodsVO`，由 Service 查询、判断存在性，Controller 返回统一响应。当前“商品不存在”基础异常已经写过，本任务复用并迁移为目标结构，不重复造一套异常。列表保留现有路径 `GET /api/goods`，详情为 `GET /api/goods/{id}`。
- **验证场景：**已有 ID 返回正确商品；不存在 ID 返回 404 `GOODS_NOT_FOUND`；非法 ID 返回合适的 400；空列表返回空数组；列表有数据时每项字段正确。
- **完成条件：**成功和失败的状态码、JSON 结构与接口文档一致；有针对读取行为的测试。只看到方法能编译还不算完成。

### T04：新增商品的输入边界与重复编码

- **业务目的：**创建商品时，客户端只填写商品资料；ID、库存和状态由服务端决定。
- **开发重点：**设计 `GoodsCreateRequest`，引入合适的参数校验；Service 显式组装 `Goods`，初始化库存 0、状态 1。依靠 `goods_code` 唯一索引兜住并发重复，再把冲突转换为 `GOODS_CODE_DUPLICATE`。创建成功返回商品详情和 HTTP 201。
- **验证场景：**合法创建并取得自增 ID；重复编码返回 409；空白名称、非法编码、负价或超过两位小数返回 400；请求夹带 `id`、`stockQuantity`、`status` 等字段时被拒绝。
- **完成条件：**数据库与响应都显示正确的初始值；失败请求没有生成半成品商品。测试只使用专门的测试数据。

### T05：修改商品资料的字段白名单

- **业务目的：**现有 `PUT /api/goods` 只能修改允许的资料字段，不能借此直接改库存或编码。
- **开发重点：**设计 `GoodsUpdateRequest`；`id` 必填且大于 0，至少提供一个可修改字段。Service 显式更新名称、分类、单位、价格，明确“未传字段”和“传 null”的处理方式。保留当前路径及按提供字段修改的语义。
- **验证场景：**只改名称或价格成功；空更新、缺 ID、非法价格返回 400；不存在商品返回 404；夹带 `goodsCode`、`stockQuantity`、`status`、时间字段时返回 400。
- **完成条件：**再次 GET 可见允许字段的变化；编码、库存、状态、创建时间等受保护字段保持原值。

### T06：商品启停用

- **业务目的：**商品可以停用，但历史资料仍能查询；后续入出库确认要拒绝停用商品。
- **开发重点：**增加专用状态请求与 `PATCH /api/goods/{id}/status`。校验状态只能为 0 或 1；事务内锁定商品行再修改，约定与单据确认一致的锁顺序。重复设置同一状态应返回稳定结果。
- **验证场景：**1→0→1、重复设置、非法状态、不存在商品；修改状态后详情能读到新值。
- **完成条件：**状态只能由专用接口改变，更新与查询一致。确认和停用的并发竞争留到 T33 再做真实并发验收。

### T07：商品分页与条件查询

- **业务目的：**商品变多后，列表不能一次返回全部记录。
- **开发重点：**增加 `GET /api/goods/page`、查询参数和分页结果对象。支持商品编码精确匹配或名称模糊匹配、状态筛选；采用参数化条件和稳定排序。实施前核对当前 MyBatis-Plus 版本的分页依赖。
- **验证场景：**第一页、最后一页、空页；关键词与状态组合；`page=0`、`size=0`、`size=101`；核对 `records`、`total`、`page`、`size`。确认 `/page` 不被 `/{id}` 错误匹配。
- **完成条件：**默认页码和大小符合接口文档，最大每页 100 条，查询结果和总数可解释。

## P2：可复建数据库与独立测试环境（T08～T12）

阶段目标：把真实数据库结构写成可审查的 SQL，并在独立测试库验证。开始任何 DDL 前，先核对现有表与数据；不清空开发库。

### T08：配置样例与 `goods` 表基线

- **业务目的：**新克隆项目的人能看懂怎样配置数据库，不依赖开发者本机的秘密配置。
- **开发重点：**只读执行 `SHOW CREATE TABLE goods`，把实际结构整理到版本化 `schema.sql`；提供不含真实用户名密码的配置样例和启用说明。T08 创建或指定一个空测试库供 T09～T11 手工验证，T12 再配置自动化测试。
- **验证场景：**按样例在空测试库创建 `goods`；对照字段、索引、约束与实际表；检查 Git 暂存文件没有密码。
- **完成条件：**可在空测试库复建商品表，开发库原有商品与库存保持不变。

### T09：入库单主表与明细表

- **业务目的：**一张入库单有多条商品明细，需要数据库保证主明细关系和基本数据合法。
- **开发重点：**在 `schema.sql` 写 `inbound_order`、`inbound_order_item`。主表保存单号、状态、时间；明细保存商品、数量和商品资料快照。检查主键、唯一单号、同单同商品唯一、外键、数量与状态约束。
- **验证场景：**合法主单和明细可写入；重复单号、重复商品行、指向不存在主单或商品的明细、数量 0、非法状态被拒绝。
- **完成条件：**测试库约束实际生效；插入草稿不改变 `goods.stock_quantity`。

### T10：出库单主表与明细表

- **业务目的：**出库需求与入库相似，但有独立单号、往来方和关联关系。
- **开发重点：**写 `outbound_order`、`outbound_order_item` 的 DDL。逐项核对外键指向出库主表和 `goods`，避免从入库 SQL 复制出错误表名。
- **验证场景：**合法出库草稿可插入；重复单号、同单重复商品、非法状态或数量、孤儿明细均失败。
- **完成条件：**出库主明细能独立使用，测试数据没有影响商品余额。

### T11：库存流水表与数量上限

- **业务目的：**每次已提交的库存变化都能追溯来源和变化前后余额。
- **开发重点：**写 `stock_movement` 的字段、唯一来源键、索引及约束；区分期初、入库、出库。核对当前 `goods.stock_quantity` 数据后，再设计与 Java `Integer` 上限一致的约束，不直接对开发库执行未经验证的变更。
- **验证场景：**合法流水写入；重复来源、前后余额不匹配、零变化、超过上限或非法来源类型被拒绝。
- **完成条件：**六张表可从空测试库复建；现有数据与新增约束的兼容性有记录。

### T12：独立 MySQL 自动化测试环境

- **业务目的：**以后跑测试时不能改动开发库中的真实学习数据。
- **开发重点：**增加测试 Profile、无密码的测试配置约定、测试数据创建和清理方式。用独立测试库验证一次实体与 Mapper 的最小读写；处理好测试结束后的清理。
- **验证场景：**运行上下文测试和最小映射测试，确认连接的数据库确实是测试库；故意失败的测试不改变开发库。
- **完成条件：**测试命令可重复，配置里没有真实密码。上下文启动通过只说明测试环境可用，不代表业务逻辑通过。

## P3：入库草稿、确认与流水（T13～T20）

阶段业务流程：创建草稿 → 查询草稿 → 确认时增加库存并写流水，或取消草稿。创建草稿不增加库存；确认、库存和流水必须同事务提交。

### T13：入库实体与 Mapper

- **业务目的：**让 Java 代码正确读写入库主表与明细表。
- **开发重点：**建立 `InboundOrder`、`InboundOrderItem` 和各自 Mapper；映射自增 ID、状态、时间、数量与商品快照。先确认字段映射，再写业务流程。
- **验证场景：**在测试库插入主单，取得生成 ID，再关联写入明细并读回；核对每个字段。
- **完成条件：**映射正确；本任务不确认单据，也不修改库存。

### T14：创建入库草稿

- **业务目的：**管理员记录准备入库的商品和数量，确认前仍可放弃。
- **开发重点：**设计创建请求，校验 1～100 条明细、正数量、同单商品不重复、商品存在且启用。服务端生成单号与商品资料快照；一个事务保存主单和全部明细。
- **验证场景：**合法多行返回草稿详情和 201；空单、重复商品、停用或不存在商品被拒绝；保存第二条明细失败时主单和第一条也回滚。
- **完成条件：**成功只留下草稿及明细，`goods` 余额和 `stock_movement` 均不变。

### T15：入库单详情与分页

- **业务目的：**能查看草稿和历史单据，知道每张单当时记录了什么。
- **开发重点：**详情组装主表与全部明细；列表按单号、状态和时间分页，只返回摘要。日期用 `[from,to)` 半开区间并限制查询跨度；展示明细里的商品快照。
- **验证场景：**存在和不存在单据、空页、状态与时间边界；创建草稿后改商品名称，历史明细名称保持原值。
- **完成条件：**详情完整，列表 `total` 正确且不对列表每行逐一加载明细。

### T16：受控增加库存

- **业务目的：**入库确认时安全增加余额，避免停用商品被入库或整数溢出。
- **开发重点：**在外层事务里按商品 ID 升序锁定行，核对启用状态和加法上限，用带条件的 SQL 增加余额并检查影响行数。记录变化前后余额供流水使用，不开放任意加库存的 HTTP 接口。
- **验证场景：**正常增加、商品不存在或停用、数量非法、接近 `Integer.MAX_VALUE`、人为抛错后回滚。
- **完成条件：**失败不留下余额变化；成功得到准确的前后余额。并发正确性以后在 T31～T33 验证。

### T17：库存流水写入

- **业务目的：**每次真正改变库存，都能说明来自哪张单据、改了多少、改前改后各是多少。
- **开发重点：**建立流水实体、Mapper 和写入方法；从确认事务传入来源及前后余额。唯一来源约束作为重复写入的最后一道保护，不能悄悄忽略冲突。
- **验证场景：**正常写入；同来源同商品重复写入失败；余额关系不正确被拒绝；外层事务回滚后流水也不存在。
- **完成条件：**流水参与确认事务，没有单独提交；不提供随意编辑或删除历史流水的接口。

### T18：现有库存的期初接入

- **业务目的：**开发库里已有商品库存，新流水系统需要一个起点解释这部分余额。
- **开发重点：**先核对现有余额和流水，制定暂停相关写入、执行与核对步骤。为正库存商品写一次期初流水，变化为 `0 → 当前余额`；余额为 0 不写零变化。期初只记账，不再次增加余额。
- **验证场景：**先在测试库演练正库存、零库存、重复执行和已有业务流水的情况；重复或不完整状态应停止并核查。
- **完成条件：**Review 后再实施开发库接入，记录执行范围、时间和对账结果；原有商品余额不变。

### T19：确认入库

- **业务目的：**把草稿正式入库，并保证单据状态、商品余额和流水一起成功或一起失败。
- **开发重点：**在一个事务中锁单据、检查状态、读取明细、按商品 ID 升序锁商品、增加余额、写流水、改成已确认。已确认单据重复请求返回原结果，已取消单据拒绝确认。
- **验证场景：**首次确认每项加一次库存并各有一条流水；重复确认不再次增加；取消单确认失败；中间抛错时整单回滚。
- **完成条件：**只在草稿首次确认时产生库存效果；失败时单据仍是草稿，余额与流水保持原值。

### T20：取消入库草稿

- **业务目的：**不再入库时保留单据记录，但不产生库存效果。
- **开发重点：**锁定主单，按状态规则完成草稿→已取消；重复取消返回已有取消结果；已确认单据不允许取消。
- **验证场景：**首次取消、重复取消、已确认后取消、不存在单据。
- **完成条件：**取消不改商品库存、不写流水；非法状态返回明确的业务冲突。

## P4：出库与防超扣（T21～T26）

阶段业务流程：创建出库草稿 → 查询 → 确认时检查库存并扣减，或取消草稿。草稿不预占库存；确认时的实际余额决定能否出库。

### T21：出库实体与 Mapper

- **业务目的：**让 Java 正确读写出库主表和明细表。
- **开发重点：**建立出库实体和 Mapper，核对主键回填、状态、时间、数量、商品快照；每个关联都指向出库表。
- **验证场景：**在测试库写入主单和多条明细，再读回检查字段与关联。
- **完成条件：**映射正确；此时仍没有扣减库存的业务行为。

### T22：创建出库草稿

- **业务目的：**记录发货需求，不在创建时承诺或扣减库存。
- **开发重点：**校验明细数量、重复商品、商品存在与启用；生成 `OUT` 单号与商品快照，事务保存主单和全部明细。沿用入库中已验证的规则，但核对出库专有字段。
- **验证场景：**合法多行创建；空单、重复商品、停用或不存在商品、明细保存失败。
- **完成条件：**成功返回 201 草稿；库存和流水始终不因创建草稿而变化。

### T23：出库单详情与分页

- **业务目的：**能查看待出库需求和历史出库记录。
- **开发重点：**详情显示主单和快照明细；列表支持单号、状态、时间筛选并分页，使用稳定排序。
- **验证场景：**存在与不存在详情、空页、过滤条件、时间边界；商品改名后历史单据仍显示原快照。
- **完成条件：**接口返回符合设计，分页总数正确，列表不加载所有明细。

### T24：受控扣减库存

- **业务目的：**库存够且商品启用时才扣减，绝不出现负库存或丢失更新。
- **开发重点：**在确认事务内使用带“余额足够”条件的扣减 SQL，检查影响行数；区分商品不存在、停用和库存不足。多商品操作采用一致的锁定顺序。
- **验证场景：**扣完恰好为 0、扣一部分、超过余额、商品停用、事务回滚。
- **完成条件：**库存不足时返回明确冲突；余额不为负，不使用“读取旧值后无条件覆盖”的写法。

### T25：确认出库

- **业务目的：**出库确认需要同时完成单据状态、扣库存和负向流水。
- **开发重点：**一个事务锁单据并核对草稿状态，按商品 ID 升序锁定并扣减，写每行一条负向流水，最后改成已确认。重复确认不重复扣减，已取消单据不能确认。
- **验证场景：**成功、重复确认、单个商品不足、多行中第二个商品不足、商品停用、中途异常。
- **完成条件：**失败后单据保持草稿，所有商品余额及流水均不变；成功后每行有准确流水。

### T26：取消出库草稿

- **业务目的：**允许放弃未确认的出库需求，保留历史状态。
- **开发重点：**锁定主单并按状态规则取消；重复取消返回原结果；已确认单据拒绝取消。
- **验证场景：**草稿取消、重复取消、已确认后取消、不存在单据。
- **完成条件：**取消草稿不加回库存，因为草稿从未扣过库存；不写流水。

## P5：库存可查询、可解释（T27～T29）

### T27：库存余额查询

- **业务目的：**管理员能直接看到每个商品当前余额，而不是通过修改商品接口查看库存。
- **开发重点：**提供单商品余额和分页列表，从 MySQL 的 `goods.stock_quantity` 读取，不建立第二份余额。区分商品不存在和余额为 0。
- **验证场景：**正库存、零库存、不存在商品、状态与关键词过滤、分页边界。
- **完成条件：**返回余额与 `goods` 一致；查询路径不依赖 Redis。

### T28：库存流水查询

- **业务目的：**能解释某个商品在一段时间内为什么增减库存。
- **开发重点：**按商品、来源、时间分页查询 `stock_movement`，核对来源类型、单号、变化前后值。时间区间和分页规则与接口文档一致；必要时用实际数据和 `EXPLAIN` 检查索引。
- **验证场景：**期初、入库、出库的筛选；空页、不存在商品、时间边界与非法日期。
- **完成条件：**排序和总数稳定，不提供修改或删除流水的 HTTP 接口；性能结论附测量依据。

### T29：库存对账

- **业务目的：**证明“当前余额 = 期初 + 已确认入库 − 已确认出库”，并能发现记录不一致。
- **开发重点：**按商品汇总流水变化量，与 `goods.stock_quantity` 比较；聚合使用足够大的数值类型。区分新商品无流水、零库存和有期初商品。
- **验证场景：**多次入出库、失败单、重复确认；测试库人为制造差异后应被检测出来。
- **完成条件：**正常案例无差异；发现差异时报告出来，而不是直接覆盖余额掩盖问题。

## P6：事务与并发验收（T30～T33）

只有 T30～T33 在**真实 MySQL、独立测试连接**下通过，才把仓库业务最小闭环标为完成。线程要真正同时竞争同一数据，并检查最终数据库状态。

### T30：多明细失败时整单回滚

- **业务目的：**一张单的第二个商品失败，不能让第一个商品已经改变库存。
- **开发重点：**在测试库准备两个商品和多行单据，设计能让第一行更新后第二行失败的场景；结束事务后用新连接读取最终数据。
- **验证场景：**分别覆盖入库和出库；检查两个余额、流水数量、单据状态，不只检查抛了异常。
- **完成条件：**所有相关数据一起回滚，没有部分成功。

### T31：同一单据被并发确认

- **业务目的：**两次同时确认同一张单，也只能产生一次库存效果。
- **开发重点：**用两个独立线程与数据库连接，在明确的同步点同时请求确认；分别测试入库和出库。收集两个线程的结果和异常。
- **验证场景：**检查最终单据已确认、余额只变化一次、每个商品只有一条对应流水。
- **完成条件：**无重复增减库存或重复流水；测试可重复运行并说明锁与幂等怎样起作用。

### T32：不同出库单争抢同一库存

- **业务目的：**多个合法出库单同时争同一批库存，不能一起成功造成超扣。
- **开发重点：**例如商品余额 10，两张草稿各要出 7；用独立连接并发确认，之后从数据库重新读取两单、余额和流水。
- **验证场景：**恰有一单成功，余额为 3，另一单保持草稿；只有成功单有出库流水。
- **完成条件：**余额不为负，没有失败单的部分扣减或流水。

### T33：确认与取消、停用的竞争

- **业务目的：**单据确认与取消、商品停用同时发生时，不能产生互相矛盾的结果。
- **开发重点：**分别构造“同单确认 vs 取消”和“确认 vs 商品停用”；覆盖两种先后提交顺序，检查单据和商品锁的顺序。
- **验证场景：**取消先完成时确认失败且无库存效果；确认先完成时库存和流水完整；停用先完成时确认被拒绝。
- **完成条件：**每次只有合法终态，锁冲突或重试也不会留下部分数据。

## P7：商品资料 Redis 缓存（T34～T36）

先完成 MySQL 业务正确性，再接入 Redis。缓存只保存不含库存的商品基础资料；库存判断始终读取 MySQL。

### T34：Redis 接入与商品资料模型

- **业务目的：**为后续缓存提供一个明确的“商品基础资料”查询入口。
- **开发重点：**引入与当前 Spring Boot 版本匹配的 Redis 依赖和无密码配置样例，设计 `GoodsCatalogVO`，建立数据库读取路径；检查该对象不含 `stockQuantity`。
- **验证场景：**本地 Redis 连接与序列化往返；资料查询返回正确字段；Redis 配置不暴露秘密。
- **完成条件：**基础资料接口可读，库存接口仍以 MySQL 为准。

### T35：缓存读取、未命中与过期

- **业务目的：**重复查询商品资料时减少数据库读取，同时保证缓存不会永久持有旧数据。
- **开发重点：**按 Cache-Aside 流程，先查缓存，未命中查数据库并写入有 TTL 的缓存；不存在商品可用短 TTL 的空标记，但不能把空标记当作商品存在。
- **验证场景：**首次回源、第二次命中、TTL 到期后回源、不存在商品返回 404；检查所有相关 key 都会过期。
- **完成条件：**命中与回源能用日志或测试证据区分，结果与数据库读取语义一致。

### T36：资料更新后失效与 Redis 故障回源

- **业务目的：**商品资料改变后缓存最终能刷新；Redis 故障不能阻断数据库核心业务。
- **开发重点：**数据库成功提交后删除相关缓存；失败回滚时不发布未提交的新资料。Redis 读写或删除失败时记录异常并回源，说明 TTL 内可能出现短暂旧值的边界。
- **验证场景：**成功修改、数据库回滚、缓存删除失败、Redis 停机；逐一核对资料查询与库存业务。
- **完成条件：**数据库结果不会被缓存错误伪装成回滚；故障时基本查询可用，不宣称缓存强一致。

- **验证场景：**商品→入库→出库→流水的完整演示，包含库存不足、重复确认、回滚与缓存故障；失败要定位并记录。
- **完成条件：**新环境可复现，没有开发库依赖或泄露的密码；测试结果和适用范围写清楚。

- **验证场景：**按 README 独立运行并演示，能解释库存不足、多明细回滚、重复确认、并发竞争以及 Redis 故障回源。

## 读到这些词时

- **DTO：**接收请求的数据结构，用来限定客户端能填写的字段。
- **VO：**返回给客户端的数据结构，避免把数据库实体直接当接口契约。
- **快照：**创建单据时保存商品当时的名称、编码等，商品后来改名也不改变历史单据。
- **幂等：**同一单据重复确认，库存效果仍只发生一次。
- **期初：**为系统接入前已有库存建立一次账目起点，不再增加现有余额。
- **对账：**比较当前库存与全部已提交变化的合计，发现缺失或重复记录。
- **回滚：**同一事务里有一步失败，之前已执行但未提交的数据库变化一起撤销。
