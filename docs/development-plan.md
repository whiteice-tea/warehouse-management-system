# 开发任务清单

版本：规划 v1，2026-10-15。以下是路线图，不表示同时安排全部任务。T01已于2026-10-19按现有接口范围完成手工验收；当前推进T02，实际进度见 [progress.md](progress.md)。

## 执行方法

每个任务预计 30～90 分钟，包含理解、编码、Review 和一次针对性验证；不熟悉的知识点可以延长或继续拆分。每次仅领取一个任务，先理解业务再写代码。

每项均列出目标、具体功能、涉及文件、开发者亲写的内容、知识点、测试和验收。文件路径默认在 `src/main/java/org/whiteicetea/warehousemanagementsystem/` 下；测试在对应 `src/test/java/` 包中。文件名是设计建议，不代表已经存在。

业务核心、SQL、DTO、错误处理和有业务断言的测试由开发者编写。导师提供思路、伪代码及 Review；没有明确请求时不提供完整实现，不擅自改业务代码。

统一完成条件：代码通过 Review，必要编译/测试成功，验收证据写入 progress。编译通过不能代替接口、事务或并发验收。

T01～T07 的接口手工联调只使用明确标记的测试商品；单元/API自动化验证先使用模拟依赖，不连接开发库。T12建立独立MySQL测试环境后补做数据库集成验证，事务和并发验收必须使用真实MySQL，不能用模拟依赖替代。

### T01：修改商品接口回归（30分钟）

- 目标/功能：验证已写的 PUT 确实修改指定商品，并核对其他字段。
- 文件：读取 `controller/GoodsController.java`、`entity/Goods.java`；证据写入 `docs/progress.md`。
- 亲自完成：开发者重启最新服务，先 GET 保存旧值，再构造 PUT 请求和修改后 GET；本任务无需新增业务代码。知识点：HTTP 方法、请求体绑定、主键定位、编译与运行进程区别。
- 测试：用实际存在的商品 ID，只改名称和价格；检查 goodsCode、库存、createdAt；失败时收集响应和对应日志。
- 验收：请求/响应及状态码齐全，修改值正确，其他关键字段保持原值。没有测试结果则仍待验收。

阶段目标：一个入库单从草稿到确认，余额、流水和状态一致；既有库存有可解释期初。每项依赖前一项通过。

- 测试：测试库写主单、回填主键、关联明细并读回。

### T14：创建入库草稿（90分钟）

- 文件：inbound DTO、InboundOrderController、Service/Impl、必要Mapper查询。
- 亲写/知识：实现明细去重检查、商品存在/启用校验、服务端单号和快照、主明细事务；学习集合处理与嵌套校验。
- 测试：合法多行、重复商品、空单、缺商品/停用商品、明细保存失败。

### T15：入库详情与分页（90分钟）

- 目标/功能：查看草稿并查询历史状态。
- 文件：入库VO、查询DTO、InboundOrderController/Service/Mapper。

- 验收：列表不携带全量明细，详情完整，total正确，31天范围约束生效。

### T16：受控库存增加（90分钟）

- 目标/功能：在外层事务内锁定商品并安全增加余额。
- 文件：InventoryService/Impl、GoodsMapper及必要XML、库存映射测试。
- 亲写/知识：写升序锁定和带上限/启用条件的增加SQL，检查影响行数；学习SELECT FOR UPDATE、整数溢出、同连接事务。
- 测试：正常增加、数量非法、不存在/停用、余额上限、强制回滚。
- 验收：无HTTP任意加库存入口，失败不会留下变化，确认流程能获得真实before/after。

### T17：流水实体与写入协作（60分钟）

- 目标/功能：库存事务可以记录来源、变化和前后余额。
- 文件：StockMovement实体/Mapper/Service/Impl及测试。
- 亲写/知识：写流水字段、校验和参与外层事务的保存方法；学习事务传播和唯一约束兜底。
- 测试：合法流水、重复来源、余额不匹配、外层事务回滚。
- 验收：流水与余额使用同一事务，重复不能静默忽略，无编辑或删除HTTP接口。

### T18：现有库存的期初接入（90分钟）

- 目标/功能：为接入前正库存建立一次期初基线。
- 文件：开发者编写受控期初SQL或一次性工具、测试用例、docs接入记录。
- 亲写/知识：先核对数据并规划暂停写入，再写事务内期初生成和重复检查；学习历史数据接入与对账。
- 测试：先在测试库执行；正库存一条、零库存无零流水、重复执行被阻止，已有业务流水时中止。
- 验收：实际实施须先Review；商品余额不被再次增加，期初合计与余额一致，有执行范围和时间记录。

### T19：确认入库（90分钟）

- 目标/功能：将单据、库存增加与流水绑定为一个事务。
- 文件：InboundOrderService/Impl、Controller、锁单据Mapper及确认测试。
- 亲写/知识：按架构伪流程实现单据锁、状态检查、商品排序锁定、余额/流水/状态提交；学习业务幂等和事务边界。
- 测试：确认增加余额；重复确认无第二次变化；取消单拒绝；途中异常整体回滚。
- 验收：只有合法草稿首次确认产生业务效果；成功每明细一条流水，失败无部分提交。

### T20：取消入库草稿（60分钟）

- 目标/功能：允许放弃草稿，保持历史。
- 文件：InboundOrderService/Impl、Controller及取消测试。
- 亲写/知识：锁定主行并实现草稿→取消，重复取消返回原结果；学习状态机。
- 测试：草稿取消、重复取消、确认单取消、不存在单。
- 验收：取消不改变库存/流水，确认单返回409而不逆向修改历史。

- 亲写/知识：写筛选、31天范围和来源说明；学习组合索引、参数化SQL及EXPLAIN。
- 测试：期初/入/出库过滤、时间边界、空页、不存在商品。
- 验收：稳定排序和total正确，无修改删除入口，索引分析不虚报性能提升。

### T29：库存对账验证（60分钟）

- 目标/功能：证明余额等于期初和已提交流水之和。
- 文件：对账查询/测试、docs验收记录。
- 亲写/知识：写按商品聚合和差异判断；学习数据不变量、空集合和整数聚合类型。
- 测试：期初后多次入出库、零库存新商品、失败单和重复确认。
- 验收：正常案例无差异；测试库人为制造差异时能发现，不能用覆盖余额“修复”测试。

## P6：MVP-B正确性验收

阶段目标：真实MySQL事务和并发证据通过，才能标记仓库业务MVP完成。每次并发测试使用独立线程、独立连接和明确同步点，不能在一个测试事务中顺序调用冒充并发。

### T30：多明细失败回滚（90分钟）

- 目标/功能：验证中间失败没有部分库存提交。
- 文件：InboundOrderServiceIntegrationTest、OutboundOrderServiceIntegrationTest。
- 亲写/知识：写两商品订单和第二步失败断言；学习事务代理、失败注入和提交后核验。
- 测试：第一商品已执行更新后第二商品失败，事务结束后从新连接查询。
- 验收：两商品余额、流水数量及单据状态均符合整体回滚，而非只检查抛异常。

### T31：同单据并发确认（90分钟）

- 目标/功能：验证两请求只能产生一次入/出库效果。
- 文件：OrderConfirmationConcurrencyTest及测试辅助数据。
- 亲写/知识：用线程池和同步工具构造两个独立事务，写最终数据库断言；学习行锁和幂等。
- 测试：两次同时确认同一入库单，再测试出库单。
- 验收：最终确认状态、单次余额变化、每商品一条流水；线程错误被显式收集。

### T32：不同出库单争抢库存（90分钟）

- 目标/功能：验证防超扣和无丢失更新。
- 文件：InventoryConcurrencyTest。
- 亲写/知识：如库存10，两张出库单各扣7，构造竞争并断言；学习数据库隔离与条件更新。
- 测试：独立连接同时确认，失败方事务完成后读取所有相关记录。
- 验收：恰有一单成功，余额3，一单保持草稿，只有成功单的流水；不存在负数或部分提交。

### T33：确认与取消/停用的竞争（90分钟）

- 目标/功能：验证状态流转和商品状态检查没有竞态。
- 文件：OrderStateConcurrencyTest、GoodsStatusConcurrencyTest。
- 亲写/知识：写独立事务的确认vs取消、确认vs停用测试；学习锁顺序和合法终态。
- 测试：通过同步点覆盖两种先后顺序，检查事务结果及流水。
- 验收：取消单无库存效果；停用先提交时确认拒绝，确认先提交时允许其完成后停用；锁冲突不留下部分数据。

## P7：Redis资料缓存

阶段目标：有实际用途和故障测试的缓存能力。依赖P6通过，本阶段才添加Redis依赖，不引入新的业务基础设施。

### T34：Redis接入与资料查询模型（90分钟）

- 目标/功能：连接本地Redis，建立不含库存的资料读取入口。
- 文件：pom.xml、示例配置、RedisConfig、GoodsCatalogVO、GoodsController/Service。
- 亲写/知识：使用Boot管理的Spring Data Redis，写序列化/超时配置及catalog数据库读取；学习缓存值边界。
- 测试：独立测试前缀下连接、序列化往返，验证VO无stockQuantity。
- 验收：原库存路径不依赖Redis，配置无密码硬编码，资料接口结构符合文档。

### T35：Cache-Aside和TTL（90分钟）

- 目标/功能：缓存命中、未命中及不存在商品路径完整。
- 文件：`cache/GoodsCatalogCache.java`、GoodsService/Impl及缓存测试。
- 亲写/知识：写先缓存后数据库、正常TTL和空标记短TTL；学习过期、穿透及序列化。
- 测试：首次回源、再次命中、到期回源、不存在商品404与短空缓存。
- 验收：缓存命中证据可重复，所有key有限TTL，不将缓存空值误当商品存在。

### T36：更新失效与故障回源（90分钟）

- 目标/功能：资料变化提交后删除缓存，Redis故障不阻断核心数据库业务。
- 文件：商品更新/状态Service、缓存类及测试；必要提交后失效协作。
- 亲写/知识：写数据库提交后删除、异常日志与回源；学习DB/Redis不共享事务和最终一致性边界。
- 测试：更新成功、数据库回滚、删除失败、Redis停机，核对返回和库存业务。
- 验收：回滚不发布未提交资料，缓存错误不把已提交数据库写伪装成回滚；文档明确TTL内可能陈旧，不宣称强一致。
