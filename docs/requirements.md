# 项目需求

版本：规划 v1，2026-10-15。实现状态见 [progress.md](progress.md)。

## 1. 背景与目标

小型仓库通过表格记录商品和库存时，容易出现重复商品编码、库存被直接改写、重复入库、超量出库，以及无法解释库存变化的问题。

本项目服务一个仓库的管理人员，提供商品档案、入库单、出库单、库存查询和库存流水。技术目标是让开发者独立掌握 REST 接口、分层设计、数据建模、事务、并发控制、测试以及有实际用途的 Redis 缓存，并能用代码和测试证据解释设计。

学习完成标准不是“接口数量足够多”，而是一次出入库能同时保证单据、库存和流水正确，且能解释失败和并发场景。

## 2. 范围与假设

| 项目 | 本版约定 |
| --- | --- |
| 仓库 | 单仓库，不区分库位，不建立重复的库存汇总表 |
| 库存单位 | 整数件数；暂不支持重量、小数、批次、序列号 |
| 商品编码 | 唯一；目标规则为大写字母、数字、短横线，1～64 字符；创建后不修改 |
| 分类、单位 | 沿用 `goods.category`、`goods.unit` 字符串，暂不新增字典模块 |
| 价格 | 商品参考价，非负且最多两位小数；不承担采购结算和财务核算 |
| 往来方 | 单据记录供应方/收货方名称，暂不维护供应商、客户档案 |
| 身份与权限 | 本版是本地单角色演示，不宣称已实现登录、权限或操作人身份审计 |
| 数据一致性 | MySQL 为库存事实来源；Redis 不决定库存是否足够 |
| 前端 | Postman 即可验收，Vue 不是后端 MVP 的前置条件 |

## 3. 核心场景

### 3.1 商品建档

管理员建立唯一商品档案，新商品库存为 0。已有测试商品可保留，不能通过商品资料接口任意调整库存。商品名称、分类、单位和参考价可以修改，商品可以停用。停用商品可查询历史，不允许新出入库确认。

### 3.2 入库

创建入库草稿 → 查看明细 → 确认入库 → 增加库存 → 生成入库流水。创建草稿不影响库存。同一张草稿重复确认只产生一次业务效果。

### 3.3 出库

创建出库草稿 → 查看明细 → 确认出库 → 校验并扣减库存 → 生成出库流水。一张单据中任意商品不足，整个确认失败，不能部分扣减。多个请求同时出库时库存不能变负。

### 3.4 取消与查询

草稿可以取消，取消不影响库存。已确认单据不可取消、修改或物理删除；业务冲销作为后续扩展。根据单号、状态和时间查询单据；根据商品和时间查询库存流水。

### 3.5 现有库存接入

现有商品已经有库存，后续增加流水时需要建立一次期初记录。期初记录解释接入时余额，不伪造历史采购单，也不重复增加库存。

## 5. MVP 分两层验收

### MVP-A：商品接口学习闭环

已有列表、详情、新增链路以及自增 ID 验证。修改方法已写，测试未确认。仍缺少业务校验、稳定错误响应和请求字段边界，因此不能称为完整商品模块。

### MVP-B：仓库业务最小闭环

目标包含六张表：商品、入库单、入库明细、出库单、出库明细、库存流水。

必须达到：

1. 商品资料可维护，库存只能通过受控流程变化。
2. 入库、出库均具备“草稿 → 确认/取消”状态流转。
3. 单据确认、库存更新和流水插入在同一个 MySQL 事务内完成。
4. 重复确认不重复加减库存，并发出库不超扣。
5. 任一商品失败时整张单据回滚；能通过流水解释余额。
6. 提供分页查询、参数校验、资源不存在和业务冲突的明确响应。
7. 有可重复执行的接口用例和关键事务、并发测试证据。

Redis 不作为 MVP-B 的正确性前提。达到 MVP-B 后再进入缓存与项目交付阶段。

## 6. 关键业务规则

- 商品名称必填，分类和单位可选；编码由服务端校验并受唯一索引约束。
- 商品参考价范围为 `0.00～9999999999.99`，使用 `BigDecimal`，拒绝超过两位小数的输入。
- Java 使用 `Integer` 表示数量，统一限制为 `0～2147483647`；单据数量必须大于 0。
- 每张单据 1～100 行，同一商品只出现一次；重复商品行直接拒绝。
- 单据状态：`0=DRAFT`、`1=CONFIRMED`、`2=CANCELLED`。仅允许草稿确认或取消。
- 本版不提供草稿修改：填写错误时取消并重新创建，减少第一版状态处理复杂度。
- 入库后库存不能超过数量上限；出库前库存必须充足。
- 同一已确认单据再次确认返回当前确认结果；确认已取消单据返回业务冲突。
- 单据内容以创建时的商品名称、编码、单位快照展示，防止档案修改影响历史解释。
- 商品停用与单据确认需要对同一商品行协调加锁，避免校验通过后状态被并发修改。
- 已确认流水不可通过 HTTP 接口编辑、删除；不开放任意库存更新接口。

## 7. 非功能要求

| 方向 | 可验收要求 |
| --- | --- |
| 一致性 | 单据、库存、流水一起成功或一起失败 |
| 并发 | 两个独立事务争抢库存时，不能发生负库存或重复流水 |
| 输入边界 | 拒绝负数、溢出、重复明细、非法状态和越权字段绑定 |
| 可维护性 | Controller 处理 HTTP，Service 编排业务，Mapper 执行 SQL |
| 可测试性 | 自动化/并发测试在独立 MySQL 测试库运行；前期 Postman 联调只使用明确的测试商品 |
| 可观测性 | 错误包含业务码，服务日志可关联单号，响应不暴露堆栈或密码 |
| 可复现性 | 提供建表 SQL、无密码示例配置和本地验收步骤 |
| 性能表述 | 分页大小最大 100；性能结论必须附数据量、环境和测量结果 |

## 8. 后续扩展

| 扩展 | 业务价值 | 前置条件 |
| --- | --- | --- |
| 商品资料 Redis 缓存 | 练习 TTL、缓存失效、故障回源 | 基础接口和库存事务已正确 |
| 登录与简单角色权限 | 区分操作身份和可访问接口 | 先单独评审方案，再决定依赖 |
| 多仓库与库位 | 同商品分仓管理 | 将余额迁入 `(warehouse_id, goods_id)` 唯一库存表 |
| 盘点与调整单 | 解释实物和账面差异 | 已有可靠流水和调整审批规则 |
| 已确认单据冲销 | 纠正错误，不改写历史 | 设计反向单据和可用库存约束 |
| 批次和有效期 | 处理食品、药品等库存 | 明确批次库存及出库顺序 |
| 库存预警与统计 | 低库存提醒、出入库趋势 | 有完整业务数据，先 SQL 后评估缓存 |
| 创建请求幂等 | 网络重试不重复建草稿 | 明确客户端请求号及唯一索引 |

暂不引入微服务、消息队列、分库分表或分布式事务。简历只描述已经实现且能够演示和解释的能力，不填写未测量的并发量或性能提升。
